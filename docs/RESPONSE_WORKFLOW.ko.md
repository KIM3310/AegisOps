# 대응 검토 워크플로

이 기능은 모델의 분석 보고서와 담당자의 검토 기록을 분리합니다. 모델 출력이나 브라우저 localStorage 값을 검토 완료 상태로 신뢰하지 않습니다. 모든 출처는 현재 합성 훈련 자료입니다. 실제 기관 매뉴얼의 검색·승인·버전 관리 시스템을 구현했다는 의미가 아닙니다.

## 화면에서 사용하기

1. `LLM_PROVIDER=demo npm run dev`로 로컬 데모를 실행합니다.
2. 합성 로그를 불러오거나 승인된 텍스트를 입력합니다. 파일 가져오기는 JSONL 레코드를 검증한 뒤 텍스트 입력으로 변환합니다. 실제 장비나 보안 서비스에 연결하지 않습니다.
3. 분석 결과에서 대응 검토를 시작합니다. 분석 보고서와 그때 제출한 로그가 변경할 수 없는 스냅샷으로 저장됩니다.
4. 일치한 원본 줄, 합성 매뉴얼의 정확한 인용, 출처 버전과 해시를 확인합니다.
5. 검토를 시작하고 각 점검 계획의 위험을 확인합니다. 다음 담당자와 미확인 사항을 메모합니다.
6. 계획 검토를 완료하거나 보완을 요청합니다. 검토 완료는 장애 복구, 실제 점검 완료 또는 변경 실행 승인이 아닙니다.
7. Markdown, JSON 또는 한컴 치환 JSON을 내려받습니다. 초안을 내보내도 초안 상태가 유지됩니다.

최근 검토 다시 열기는 입력 첫 화면에서 제공합니다. 새로고침으로 이전 분석 보고서가 복원됐다면 **Start New**로 입력 화면에 돌아간 뒤 **최근 검토 서버에서 다시 열기**를 선택하세요. 이는 다른 사건의 분석 보고서 안에 이전 검토를 잘못 표시하지 않기 위한 경계입니다. 검토를 열 때마다 ID로 서버에 다시 요청합니다. 저장된 브라우저 상태만으로 검토 완료 표시를 복원하지 않습니다. 단, 조회한 뒤 다른 운영자가 상태를 바꿀 수 있으므로 현재 상태는 서버 새로고침으로 확인합니다.

## 상태와 차단 조건

```text
draft → in-review → reviewed
                  ↘ changes-requested
```

- 종료된 검토는 다시 열어 쓰지 않습니다. 보완한 자료는 새 제출 스냅샷으로 시작합니다.
- 완료에는 모든 점검 계획의 명시적 확인과 검토 메모가 필요합니다.
- 일치하는 텍스트 근거가 없으면 완료할 수 없습니다.
- 이미지는 이 저장소가 보관하거나 다시 검사하지 않습니다. 이미지를 포함한 제출은 근거 공백을 표시하며 완료를 막습니다. 필요한 관측값을 출처 시각과 함께 텍스트로 보완한 새 초안을 만드세요.
- 오래된 revision이나 중복 명령은 409로 거부합니다. 먼저 서버의 최신 상태를 다시 불러옵니다.
- 저장 실패나 손상된 파일은 성공한 검토로 처리하지 않습니다.

## API

| 요청 | 동작 |
| --- | --- |
| `POST /api/response-workflows` | 제출 스냅샷을 파싱하고 합성 출처에 연결한 초안 생성 |
| `GET /api/response-workflows/:id` | 저장된 근거·출처·상태를 검증한 뒤 조회 |
| `POST /api/response-workflows/:id/review` | expectedRevision과 검토 명령으로 상태 변경 |
| `GET /api/response-workflows/:id/export?format=markdown` | 서버의 저장값으로 Markdown 인계서 생성 |
| 같은 경로의 `format=json` 또는 `format=hancom-json` | 전체 JSON 또는 텍스트 치환용 JSON |

요청은 256 KiB 이하입니다. 검토 로그는 분석 제공자의 설정과 별개로 50,000자·1,000줄 이내입니다. MAX_LOG_CHARS를 크게 설정해 분석이 성공했더라도 이 검토 한도는 늘어나지 않습니다. 화면은 제출 전에 같은 스키마로 검사하고, 초과하면 입력 범위를 줄여 다시 분석하라고 안내합니다. 원문을 조용히 잘라 검토한 것으로 표시하지 않습니다. JSONL 가져오기는 별도의 더 좁은 경계인 100개 레코드·입력 100,000자·변환 로그 20,000자를 적용합니다. 필수 필드와 개별 길이 제한은 [공유 스키마](../shared/responseCase.ts)와 [가져오기 모듈](../services/securityEventImport.ts)에 정의합니다.

합성 API 입력 예시는 [response-workflow.synthetic.json](../samples/response-workflow.synthetic.json)입니다. 로컬 데모에서 다음 요청으로 초안을 만들 수 있습니다. 이 예제는 AI 호출이나 작업 실행을 하지 않습니다.

```bash
curl --fail-with-body \
  -H 'Content-Type: application/json' \
  --data-binary @samples/response-workflow.synthetic.json \
  http://127.0.0.1:8787/api/response-workflows
```

응답의 id와 revision을 사용합니다. 검토 시작 명령은 다음 형태입니다.

```json
{"expectedRevision":1,"command":{"kind":"begin"}}
```

완료 명령의 acknowledgements에는 서버가 반환한 모든 checkId와 `acknowledged: true`를 넣습니다. 클라이언트가 actor, 출처 내용, 해시, 상태를 정하지 않습니다.

## 인증과 저장

- 인증을 설정하면 조회와 모든 내보내기에도 자격 증명이 필요합니다. 브라우저에서는 운영자 로그인으로 HttpOnly 세션을 사용합니다.
- 공유 토큰은 `shared-token`으로 기록합니다. 개별 사람의 신원이나 결재 권한을 증명하지 않습니다.
- OIDC의 경우 서버가 검증한 subject를 기록합니다. Google Workspace 데모 로그인은 이 검토 인증과 별개입니다.
- 인증이 없는 기본 데모는 loopback 연결과 로컬 호스트명에서만 허용하며 `local-demo`로 기록합니다. 외부에 프록시로 공개하는 운영 구성을 위한 권한 체계가 아닙니다.
- HTTP에서 인증 화면을 시험할 때만 `AEGISOPS_OPERATOR_SESSION_SECURE=false`를 사용합니다. 실제 인증 배포에는 HTTPS와 Secure 쿠키가 필요합니다.
- 검토 저장은 동일 출처를 검사합니다. 기본 Vite 프록시는 브라우저의 Host를 보존합니다. 다른 프록시도 원래 Host와 프로토콜이 신뢰할 수 있게 전달되도록 구성해야 하며, 동작 편의를 위해 출처 검사를 끄면 안 됩니다.
- 파일은 기본 `.runtime/response-cases`에 저장합니다. `AEGISOPS_RESPONSE_STORE_PATH`로 경로를 지정할 수 있습니다. 이 경로를 공개 정적 디렉터리로 두지 마세요.
- 파일 기록은 임시 파일과 rename을 사용합니다. 동시 검토는 단일 Node.js 프로세스 안에서 직렬화합니다. 다중 프로세스·다중 서버 동시 쓰기를 지원하지 않습니다.
- 파일은 암호화·전자서명·감사 원장·기관별 격리를 제공하지 않습니다. SHA-256은 내용 연결과 일관성 검사이며 저장소 관리자의 위변조를 막는 서명이 아닙니다.
- 보존 기간, 용량 할당량, 삭제·백업·복구 정책은 별도 운영 과제입니다. 실제 기관 자료를 넣기 전에 승인과 운영 설계가 필요합니다.

## 한글 인수인계

한컴 치환 JSON에는 template_placeholders와 검토 상태·출처 주의사항이 있습니다. 모든 치환값은 문자열입니다. `templateValidated: false`는 실제 기관 서식을 검증하지 않았다는 뜻입니다.

[치환 문자열을 넣은 템플릿 본문 예시](../samples/incident-handover-template.txt)도 제공합니다. 이 텍스트를 HWP 파일로 이름만 바꾸어 사용하면 안 됩니다.

JSON과 본문 예시는 `.hwp` 또는 `.hwpx` 파일이 아닙니다. Windows, Hancom, pywin32가 있는 환경에서 템플릿과 줄바꿈·긴 내용·누락 항목을 별도로 시험해야 합니다. 연결의 실제 범위는 [저장소 연계 문서](INTEGRATION_MAP.ko.md)를 참조하세요.
